# Архитектура US-GPS

**US-GPS** — архитектурный подход для realtime-приложений с четким разделением ответственности и однонаправленным потоком данных.

Схема состоит из двух независимых частей:
- **US** — клиентская часть (UI + Store)
- **GPS** — серверная часть (Gate + Pipeline + Services)

Каждую часть можно использовать отдельно. GPS — это полноценная серверная архитектура, которая работает и без US-клиента.

## Ключевые принципы

Слои изолированы и образуют однонаправленный поток зависимостей:

```
Gate → Pipeline → Services
```

Верхний слой ничего не знает о внутреннем устройстве нижнего. Это позволяет менять реализацию любого слоя без влияния на другие.

## GPS (сервер)

GPS — самостоятельная серверная архитектура. Её можно применять отдельно от US: например, для API-сервисов, обработчиков вебхуков, фоновых воркеров, микросервисов. Клиент при этом может быть любым — веб, мобильный, CLI, другой сервис.

### Gate

- **Зачем:** Отделить протокол (WebSocket/HTTP/CLI) от бизнес-логики.
- **Что делает:** Принимает запросы, проверяет авторизацию, валидирует входные данные, вызывает `Pipeline`.
- **Что не делает:** Не содержит бизнес-логики, не работает с БД, не отправляет события.

### Pipeline (Flow)

- **Зачем:** Оркестрировать сложные бизнес-процессы.
- **Что делает:** Управляет последовательностью шагов, вызывает `Services` для выполнения работы, управляет транзакциями.
- **Что не делает:** Не содержит бизнес-правил, не импортирует `Gate`.

### Services (S)

- **Зачем:** Предоставить независимые, переиспользуемые возможности для работы с данными, логикой и событиями.
- **Что делает:** `Pipeline` вызывает эти сервисы для выполнения конкретных задач. Они не зависят друг от друга и обмениваются данными только через `Pipeline`.
- **Что не делает:** Не импортирует `Gate` и `Pipeline`. Сервисы не зависят друг от друга.

#### Состав Services

Состав сервисов **не фиксирован**. `Core`, `DB`, `Emit` — это лишь типовые примеры, которые подходят большинству проектов. В `Services` может лежать что угодно, что нужно вашему приложению:

| Пример сервиса | Зачем |
|---|---|
| **Core** | Чистая бизнес-логика: правила, расчеты, валидация. Без побочных эффектов. |
| **DB** | Работа с базой данных: чтение и запись. |
| **Emit** | Отправка событий клиентам (WebSocket, SSE, шина). |
| **Cache** | Кеширование (Redis, in-memory). |
| **Queue** | Постановка и обработка фоновых задач. |
| **Mailer** | Отправка email. |
| **Storage** | Работа с файлами (S3, локальное хранилище). |
| **Search** | Полнотекстовый поиск (Elasticsearch, Meilisearch). |
| **Auth** | Аутентификация и авторизация. |
| **Payment** | Интеграция с платежными системами. |
| **Logger** | Структурированное логирование. |

Правила для сервисов остаются неизменными:
1. Сервис не зависит от других сервисов.
2. Сервис не знает про `Pipeline` и `Gate`.
3. Вся координация между сервисами — через `Pipeline`.

Такой подход делает `Services` расширяемым: добавление нового сервиса не требует изменений в других сервисах и не ломает существующий код.

## US (клиент)

Клиентская часть отвечает за отображение данных и синхронизацию состояния с сервером.

### UI

- **Зачем:** Отделить представление от данных и логики.
- **Что делает:** Отображает данные из `Store`, принимает ввод пользователя, передает команды в `Store`.
- **Что не делает:** Не содержит бизнес-логику, не работает с сервером напрямую, не хранит состояние.

Состав:

- **Elements** — атомарные компоненты без логики (кнопки, карточки, поля ввода).
- **View** — читают данные из `Store`. Только отображение.
- **Edit** — изменяют данные через `Store` (вызывают `Invoke`).
- **Page** — собирают `View`, `Edit` и `Elements` в страницу.

### Store

- **Зачем:** Управлять состоянием и синхронизировать его с сервером.
- **Что делает:** Хранит данные, обрабатывает запросы, обновляет состояние при ответах от сервера.
- **Что не делает:** Не содержит бизнес-логику, не знает о `UI`.

Состав:

- **State** — данные и редьюсеры для их изменения.
- **Entity** — объединяет `State`, инициализацию (загрузка данных) и подписки на обновления от сервера. Управляет жизненным циклом данных (init/clean).
- **Invoke** — отправка запросов на сервер. Получает ответ, обновляет `State` через редьюсеры.

## Потоки данных

### Запрос

1. **UI → Store** (команда).
2. **Store → Gate** (запрос по сети через Socket.IO v4).
3. **Gate → Pipeline** (вызов).
4. **Pipeline → Services** (Core, DB, Emit или любой другой сервис).
5. **Ответ:** `Pipeline → Gate → Store → UI`.

### Событие

1. Серверное событие → **Pipeline**.
2. **Pipeline → Emit** (или другой сервис публикации).
3. **Emit → Entity** (на клиенте) через Socket.IO v4.
4. **Entity → State** (обновление).
5. **State → UI** (перерисовка).

## Почему GPS можно использовать отдельно

GPS не зависит от US. Это полноценная серверная архитектура, которая решает три задачи:

1. **Прием внешних запросов** — через `Gate` (HTTP, WebSocket, CLI, cron).
2. **Оркестрация бизнес-процессов** — через `Pipeline`.
3. **Выполнение работы** — через `Services`.

Клиент может быть любым:

- Веб-приложение на React/Vue/Svelte.
- Мобильное приложение.
- CLI-утилита.
- Другой сервис (в микросервисной архитектуре).
- Вебхук от внешней системы (например, Directus).

GPS не знает, кто именно обращается к нему через `Gate`. Это делает архитектуру универсальной: одно и то же ядро обслуживает разные типы клиентов, а добавление нового клиента не требует изменений в серверной части.

## Итог

**US-GPS** разделяет приложение на две независимые части:

- **US** — клиент: `UI → Store`
- **GPS** — сервер: `Gate → Pipeline → Services`

**Ключевые свойства архитектуры:**

- Однонаправленный поток зависимостей.
- Слои изолированы и тестируемы.
- `Services` — расширяемый набор независимых сервисов. `Core`, `DB`, `Emit` — лишь примеры.
- GPS можно использовать отдельно от US для любого типа клиентов и задач.
- Изменения в одном слое не влияют на другие.
